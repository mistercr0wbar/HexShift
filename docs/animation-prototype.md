# Animation prototype

Recommendation: **no-go** for production. This page is a standalone proof. It does not change how Hex Shift opens still images, it does not ship inside the editor, and it does not promise animation in v4.

## Why this is a no-go

1. The pinned still-WebP codec is `@jsquash/webp@1.5.0`. Its codec README names libwebp v1.0.2. `module.version()` returns 1.1.0 on both the decoder and the encoder. That is older than the 1.3.2 fix for CVE-2023-4863. Do not decode an untrusted WebP with this prototype, and do not ship this wasm in the editor.
2. The Windows host was not run. `animation-prototype.html` is not inside `HexShift.exe`. Chromium, Firefox, and WebKit here are a stand-in for the page, and that stand-in is not a Windows pass.
3. The production page's Content Security Policy cannot instantiate wasm. This prototype has its own policy, including `script-src 'wasm-unsafe-eval'` and `connect-src 'none'`. Putting the codec into `HexShift.html` would change the portable shell and needs a product decision.
4. The GIF encoder stores an exact palette only. A pixel whose alpha is neither 0 nor 255 throws "GIF cannot store partial transparency." More than 256 colours throws "GIF palette is larger than 256 colours." There is no quantizer.

## What was built

`animation-prototype.html` is generated by `scripts/build-animation.mjs` and is not imported by `src/app.js`. The product version stays 3.13.0. `HexShift.html` and `sw.js` stay the 3.13.0 shell `146cbe8a5f493454`. The production service worker's precache list does not include this page.

The WebP wasm is embedded. The page does not fetch it. The non-SIMD binaries are the ones in the build: `webp_dec.wasm` (137,960 bytes) and `webp_enc.wasm` (281,261 bytes). `webp_enc_simd.wasm` is not used, so one binary is reviewed, including on this machine. After init, each module's `HEAPU8` buffer is 16,777,216 bytes. That heap is codec memory. It is not counted in the 128 MiB application budget. `wasm-feature-detect@1.9.0` is only a transitive dependency of the package. This prototype does not call it and does not import the package's `encode.js` (that file selects the SIMD build).

Licences reviewed for this pin: the `@jsquash/webp` package is Apache-2.0. `codec/LICENSE.codec.md` is the libwebp BSD-3-Clause notice, Copyright (c) 2010, Google Inc., and the generated page includes that notice. `wasm-feature-detect` is Apache-2.0. GIF decode and encode are Hex Shift code. gifuct-js and gifenc were read as algorithm references and were not added as dependencies.

## Envelope

512 pixels on a side, 100 frames, 16 MiB of input, and 128 MiB of application-owned animation buffers. The owned estimate is `width * height * 4 * (frames + 3)`: the published frames, the canvas, one disposal snapshot, and one patch. A newer decode or encode supersedes the previous one. An aborted signal throws `AbortError`. `close()` drops the published pixels. Cancellation, a superseded decode, and `close()` release the application buffers they tracked.

Codec and native memory are separate. On this machine, after a 4×2 two-frame WebP round trip, the decoder and encoder heaps were 16,777,216 bytes each, and the application peak for that image was 96 bytes. Windows native memory was not measured.

## Behaviour the proof covers

An animation is two or more frames. A one-frame GIF, and a one-frame WebP written with the default disposal and blend, are still files. A WebP animation container sets `containerAnimated` from the VP8X animation bit; frame count still decides `animated`.

GIF delays are centiseconds. WebP durations are milliseconds. A duration of 0 is kept. The encoder always writes a Netscape 2.0 loop block. A missing loop on decode is unknown (`null`), not a guessed count. Loop 0 means infinite. One pass of frames is decoded. The loop count is not unrolled.

GIF disposal 0 is treated as do-not-dispose. Disposal 2 clears that frame's rectangle to transparent when the frame has a transparent index, and otherwise to the logical-screen background colour. Disposal 3 restores the rectangle from before the draw. The still-image importer is unchanged: `inspectRaster` of a two-frame GIF is still `image/gif` with `still: true` and no downscale proposal.

WebP blend uses the container's non-premultiplied sRGB formula. 50% green `(0,255,0,128)` over opaque red `(255,0,0,255)` rounds to `[127, 128, 0, 255]`. Disposal 1 fills that frame's rectangle with the animation background before the next frame. Partial frames stay inside the file's canvas.

Colour samples are taken from the composited frames. The same point is stable across frames until `close()`.

The built page's built-in sample encodes a two-frame GIF and a two-frame WebP, checks the blend, and reports libwebp 1.1.0. On Chromium, Firefox, and WebKit the only request was `/animation-prototype.html`.

## If a later production milestone is assigned

These are proposed semantics. They are not implemented in the editor.

- Export a composited frame, or a ZIP of composited frames, through the existing still finish path.
- The canvas bounds are the bounds stored in the file and stay fixed.
- A polygon, a brush, and a connected selection are canvas coordinates. They apply to every frame the same way.
- A session that stores frames needs `hexshift-session` version 2, so an older reader rejects the file instead of dropping the frames. This prototype does not bump the session version.
- Windows would need `image/gif` added to `ExportTypes` before a GIF save is accepted. Unknown MIME types are dropped.
- The production service worker would have to gain an explicit decision before it precaches any animation page.

## Gaps that stay open

The Windows host was not executed. The encoder's full 4096-code LZW table was not given its own test. A one-colour GIF is accepted by the palette check and was not given a separate padding test. Animated WebP was not asserted through `inspectRaster`. This recommendation does not treat those gaps as passes.
